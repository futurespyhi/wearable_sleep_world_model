# AI 协作与实验事实追踪

本仓库是网页 ChatGPT / Claude、HPG 上的 Codex 与研究者之间的共享事实来源。任务意图、已接受的方案、实现版本与实验结论都应在这里有可追踪的记录；网页对话、会话摘要和演示文稿不能替代这些记录。

当前协作链为：

```text
网页 ChatGPT / Claude：规划、文献核查、任务草案、写作
        ↓
GitHub issue + 版本化任务 spec：目标、证据、边界、完成条件
        ↓
HPG Codex：检查代码与数据、实现、按任务授权运行、保存结果
        ↓
GitHub reports + CURRENT_STATUS：运行事实、失败、结论边界
        ↓
网页 ChatGPT / Claude：核对证据、提出下一步、更新写作
```

这是一套交接约定，不是自动调度系统。创建 issue、修改状态或写下建议都不会自动启动作业。当前仓库准备工作也不代表已经运行新实验。

## 1. 各角色负责什么

| 角色 | 主要输入 | 应交付的内容 |
| --- | --- | --- |
| 网页 ChatGPT / Claude | 明确的仓库 commit、当前状态、spec 和报告 | 有出处的研究判断、可执行任务草案、待明确问题、论文或汇报草稿 |
| GitHub 任务记录 | 研究目标与现有证据 | 固定目标、信息截止、数据划分、比较方法、指标、预算、完成与停止条件 |
| HPG Codex | 已授权任务、明确的 base commit 和 spec 版本 | 实现、检查记录、作业与产物定位、实验报告、状态更新 |
| 研究者 | 任务方案和实际证据 | 确定研究方向与授权范围、解决影响任务目标的未决取舍 |

网页工具如果不能直接访问 GitHub，应接收带路径和 commit 的文件内容，返回可落入仓库的修改建议；不要声称已读到它实际无法访问的文件，也不要把待应用文本当成已合并版本。

## 2. 事实入口与阅读顺序

开始工作时按下列顺序恢复上下文：

1. 读取根目录 `CURRENT_STATUS.md`，确认当前任务、最近完整运行、正在阻塞的问题及关联报告。
2. 读取对应 issue 和 `specs/` 中的任务 spec，核对状态、`base_commit`、预先成功标准与已授权范围。
3. 读取 `reports/` 中对应 `run_id` 的实验报告，再按报告定位 protocol、manifest、metrics 和日志。
4. 对照实现版本检查本地代码与环境；若与报告使用的版本不同，明确指出差异后再解释结果。

具体实验事实以可追溯的运行清单、指标与报告为依据。`CURRENT_STATUS.md` 是索引和状态摘要；spec 说明计划；issue 和讨论记录决策过程。发现彼此矛盾时，记录冲突并核对原始运行证据，不用较新的叙述自动覆盖较旧的事实。

论文、slides 和 Canva 是面向读者的输出。它们应引用报告中的 `run_id`、结果表与结论边界；排版或措辞修改不会产生新实验事实。

## 3. 一个任务至少要固定的内容

可先使用仓库的研究任务 issue 表单，再把需要版本冻结的详细方案放入 `specs/`。任务应明确：

- **身份与起点：** issue 编号或任务 ID、spec 路径和版本、完整 `base_commit`、依赖任务、授权依据。
- **问题与依据：** 当前证据、可检验假设、要解决的具体目标，以及哪些内容仍只是提议。
- **实验定义：** 输入在什么时刻截止、目标是什么、预处理在哪一集合拟合、参与者/夜晚划分和封存规则。
- **比较与验收：** 基线、消融、主次指标及分母、预先成功标准、完成条件、失败或停止条件。
- **执行边界：** CPU/GPU、内存、时限、存储和下载预算、可用数据与环境、预期报告和产物位置。

`base_commit` 必须是明确的代码起点，不能只写会移动的 `main` 或“最新版本”。本地已有未提交修改时，应先识别并记录它们的归属；不要静默把别的任务修改并入本任务。

## 4. 方案状态与授权

建议用以下方案状态，避免把草稿当成已决定的实验：

| 状态 | 含义 |
| --- | --- |
| `proposal` | 候选方案，尚未被接受，不构成自动执行指令。 |
| `accepted` | 任务目标和范围已被接受，记录对应用户指令或决策出处。 |
| `in_progress` | 正在实施已授权任务。 |
| `blocked` | 已触及具体数据、环境、资源或任务定义障碍，记录下一步所缺信息。 |
| `completed` | 达到任务定义的交付条件；不等于科学假设成立。 |
| `superseded` | 被另一份明确关联的新方案取代，历史方案仍可查。 |

用户已经授权的实现、检查、修复或实验，应在该范围内继续推进；`accepted` 是已有决定的记录，不是额外审批关卡。普通可逆实现选择可以由执行者依据任务作出并说明。不要要求用户为同一授权重复确认，也不要把网页模型的建议自动升级为授权。

当行动超出现有授权或有影响目标的关键条件无法确定时，应先完成不依赖该决定的工作，再提出一个具体问题，说明缺少什么及其影响。任务中的数据封存、资源上限和成功标准是实际边界；需要改变时，记录变更理由、观察过的结果以及新 spec 版本，避免把结果产生后的改动称为预先决定。

## 5. 代码与运行如何关联

每次实际运行分配唯一 `run_id`，并区分以下身份：

- `base_commit`：开始该任务时依据的代码版本。
- `code_commit`：实际运行代码所属的 commit；不能用后来编写报告的 commit 代替。
- `dirty` 与 source snapshot：实际运行时是否有未提交修改；如有，保存可定位的补丁或源代码快照及 hash。
- `spec_revision` / `protocol_sha256`：运行采用的任务定义与协议。
- `data_manifest_sha256`：数据版本、固定选样、划分和输入来源的记录。
- `run_id` / scheduler job ID：逻辑实验与具体调度作业分别追踪；一个实验可能有预检、获取、审核、评分等多个 job。

冻结运行记录后，再改代码或协议应创建新的运行身份，或明确记录恢复阶段及其来源。失败日志和原始结果应保留；不能覆盖历史结果后继续沿用原结论。恢复运行要说明哪些输入被复用、哪些阶段重新执行、实际使用了哪个版本。

## 6. HPG 执行与交付

执行者首先读取仓库及 HPG 工作区适用的运行规则。下载、批量校验、数据聚合、模型运行与测试按既定 HPG 规则在分配的计算节点执行；GitHub issue 本身不授予无限资源，也不触发调度。

实现和运行后使用 [实验报告模板](../templates/EXPERIMENT_REPORT.md) 记录结果。报告至少区分 `not_started`、`running`、`completed`、`failed`、`blocked`、`not_applicable` 等阶段状态：数据获取成功不等于审核成功，审核成功不等于模型评分完成，作业退出码为零也不等于假设成立。

一次交付应包含：

1. 更新或新增 `reports/` 中以 `run_id` 对应的报告；非实验任务明确写“未运行实验”。
2. 更新 `CURRENT_STATUS.md`，关联任务、spec、报告、代码版本和下一项可执行工作。
3. 在任务记录中说明实际完成/停止位置、检查结果、仍未解决的问题及产物路径。
4. 给出允许的结论与尚未建立的结论，保留负结果、失败与不完整覆盖。

仓库中的文档之间使用相对链接。HPG 的 Orange/Blue 绝对路径可以作为带主机/存储说明的 artifact locator 写在代码格式中，但不能伪装成 GitHub 可访问链接；外部读者需要的指标摘要、清单和说明应在报告中可读。不要假设网页工具能直接访问 HPG 文件系统。

提交、推送、发布或创建远端 issue 按当前用户授权执行；在只准备本地仓库的任务中，完成文件本身即可，不应声称远端已同步。

## 7. 网页复核与下一轮交接

网页模型复核时应明确使用哪个 commit 和哪些 `run_id`，分别检查问题定义、数据覆盖、比较公平性、指标分母与结论是否匹配。它可以提出下一轮 `proposal`，但不应回写既有实验的预先标准，也不应把尚未运行的对照写成已有结果。

交接摘要建议使用下面的最小格式：

```text
任务 / issue：
读取的仓库 commit：
spec 路径与 revision：
方案状态 / 已有授权依据：
关联 run_id / report：
已经确认的事实：
当前阻塞或未决问题：
下一项具体行动与完成条件：
```
